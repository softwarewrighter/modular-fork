Running Mojo and X_eTaL on the Arduino UNO Q's Adreno 702 GPU
1. Executive assessment
Your goal is to turn the Arduino UNO Q into a small, inexpensive, heterogeneous computing platform where the same parallel algorithms can be expressed in Mojo and X_eTaL, executed on the Qualcomm Adreno 702 GPU, and compared against CPU implementations.

I would approach this as a complementary project to your existing X_eTaL GPU and FPGA work, with one important architectural decision:

Use Vulkan compute as the initial common GPU execution backend, rather than attempting to make Mojo's native GPU runtime support Adreno immediately.

That gives you a relatively short path to actual GPU execution in X_eTaL, a practical interoperability path for Mojo, and a longer-term research project involving native Mojo GPU support.

gpu-core defines the abstract device and kernel interfaces. gpu-vulkan implements those abstractions using Vulkan. gpu-ffi exports a stable C ABI so both Mojo and X_eTaL can use it.

For the Rust Vulkan implementation, consider:

ash — low-level Vulkan control; best when you want to understand exactly what the hardware does.

vulkano — higher-level Rust abstractions; potentially easier to develop against.

wgpu — attractive for portability, but its supported Vulkan feature requirements must first be checked against Turnip.

I would start with ash, or a minimal proven Vulkan compute implementation built with it. It gives you the greatest control over compatibility requirements on this constrained device.

4.2 Stable ABI design
Do not expose Rust-specific structures or compiler-dependent object layouts directly to Mojo or X_eTaL.

Use opaque handles:

typedef struct gpu_context gpu_context;
typedef struct gpu_buffer gpu_buffer;

int gpu_create(gpu_context **ctx);
int gpu_alloc(
    gpu_context *ctx,
    size_t bytes,
    gpu_buffer **out
);
int gpu_upload(
    gpu_context *ctx,
    gpu_buffer *dst,
    const void *src,
    size_t bytes
);
int gpu_dispatch(
    gpu_context *ctx,
    const char *kernel,
    gpu_buffer **args,
    size_t nargs,
    size_t count
);
int gpu_download(
    gpu_context *ctx,
    gpu_buffer *src,
    void *dst,
    size_t bytes
);

This is an illustrative API, not a complete production ABI. The implementation should also provide explicit buffer release, error messages, synchronization, kernel argument metadata, and ABI versioning.

An important design choice is to keep GPU buffers resident across multiple operations. Otherwise, you could spend more time copying and synchronizing than computing.

5.2 Two stages of GPU support
Stage A — Library calls: X_eTaL invokes existing GPU kernels. For example, a ReLU library function dispatches a precompiled SPIR-V shader.

This is practical, relatively simple, and a good starting point.

Stage B — Generated kernels: X_eTaL's compiler transforms a suitable array expression into a GPU kernel.

A possible compilation pipeline is:

X_eTaL array expression

Typed array / shape-aware intermediate representation

CPU lowering
GPU kernel lowering
Rust / native CPU
SPIR-V
I would initially generate GLSL compute shaders and compile them to SPIR-V with glslangValidator or glslc. This is easier to debug than immediately generating SPIR-V instructions.

Later, consider direct SPIR-V generation using Rust's rspirv or an intermediate representation that can also serve the FPGA compiler.

One X_eTaL-specific concern is broadcasting. Since your current language primarily implements APL-style scalar extension rather than general NumPy broadcasting, the GPU lowering must preserve the language's actual shape semantics. It should reject unsupported broadcasting rather than silently adopting different rules on the GPU.

That is a useful correctness test for the compiler as well as the backend.

Limitation: The GPU kernels are not truly authored in Mojo yet. Mojo is orchestrating externally compiled shaders.

This is the most interesting middle-term research project.

MLIR has GPU-related dialects and SPIR-V infrastructure, but that does not mean Mojo's existing GPU lowering can simply be redirected to SPIR-V.

You would need to investigate:

Whether Mojo's kernel-level intermediate representation is accessible in the available compiler tooling.

Whether its thread indexing, memory spaces, barriers, and synchronization operations can be represented in SPIR-V.

Whether the necessary SPIR-V target environment is compatible with the Adreno driver.

Whether a suitable Vulkan host runtime can launch the generated kernels.

Which parts of the compiler are available to modify.

The last question matters. Your Modular fork is useful for experimentation, but the public repository does not necessarily include every component of Modular's production compiler.

I would not commit to native Mojo-to-SPIR-V compilation until you can demonstrate a complete minimal kernel lowering path.

Milestone 1 — First actual GPU computation
Target: 2–4 days, assuming the driver works

Build the smallest possible Vulkan compute application in Rust using ash.

The shader can be intentionally simple:

#version 450

layout(local_size_x = 64) in;

layout(set = 0, binding = 0) readonly
buffer InputA {
    float a[];
};

layout(set = 0, binding = 1) readonly
buffer InputB {
    float b[];
};

layout(set = 0, binding = 2) writeonly
buffer Output {
    float result[];
};

layout(push_constant) uniform Params {
    uint count;
} params;

void main() {
    uint i = gl_GlobalInvocationID.x;

    if (i < params.count) {
        result[i] = a[i] + b[i];
    }
}
Compile it:

glslangValidator -V \
    shaders/vector_add.comp \
    -o shaders/vector_add.spv

The Rust host must create buffers, allocate and bind memory, create a descriptor set and compute pipeline, record dispatch commands, submit work, wait for completion, and retrieve results.

Begin with 1,024 elements, then increase to 1 million and 16 million elements if memory permits.

Use a CPU reference to validate every element.

Do not optimize yet. The first success criterion is correctness on physical GPU hardware.

9.3 Performance expectations
The Adreno 702 is a low-power embedded GPU. It may accelerate sufficiently large data-parallel workloads, but small kernels can easily lose to the Cortex-A53 CPU because of dispatch and synchronization overhead.

The relevant question is not merely:

Is the GPU faster?

It is:

At what workload size does the GPU become faster, and how does that crossover change when multiple operations are fused and data remains GPU-resident?

That is an excellent educational demonstration for X_eTaL and Mojo.

My recommendation
Start with the 2 GB UNO Q, Rust ash, Vulkan compute, and a vector-add/ReLU proof of concept. Use the result to build a reusable GPU backend that X_eTaL can call through its extension mechanism.

In parallel, perform a narrow Mojo ARM64 feasibility test. Do not modify the Mojo compiler until you know the device driver works and the Mojo host runtime can execute on the board.

The most important architectural distinction to preserve is:

GPU execution support is not the same as GPU code-generation support.

The first can be achieved by invoking Vulkan kernels from either language. The second requires actual compiler lowering from Mojo or X_eTaL expressions into GPU-executable code.

I would make those separate milestones, separate test suites, and separate claims in the public demos. That will make the comparison technically credible and help identify precisely where each language needs improvement.

For the next concrete step, the most useful input is the output of vulkaninfo --summary, vulkaninfo's compute queue details, and clinfo from your 2 GB UNO Q. Those will determine whether Vulkan is the correct first backend or whether we should pivot to OpenCL before designing more code.
